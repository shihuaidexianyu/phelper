cargo build --release -p phelper-desktop --features experimental    # 功耗实验需要

**纪律**：新旧控制器与 OGH 不并行写入；每项开始前 `control status` 确认

## 1. V5 — PresentMon ETW 实测（先行项）

**背景**：上次（2026-09-05）普通令牌下 ETW Access Denied，帧统计全链路无
实测报告。本项是 V1 的前置能力。

**前置**：安装包含 PresentMon 2.5.1（`tools\`）；或 dev 运行
`scripts\install-presentmon.ps1`。一个正在绘制的目标进程（游戏）。

**操作**：

```powershell
# 途径一：desktop 验证页（推荐，含硬件快照与配置上下文）
#   性能页确认 profile 已应用 → 验证页输入游戏 PID / 秒数 / 标签 → 开始采集
# 途径二：CLI 侧自检（确认子进程可拉起）
.\target\release\phelper-cli.exe telemetry --duration 30
```

采集参数：5–300 秒、同一 PID、预期 ≥100 有效帧间隔（低于 100 报告会拒绝，
这是设计行为）。

**通过标准**：
- 产出至少 1 份有效报告（CSV + JSON 均落 `measurements\`）；
- JSON 内 `frames.mean_fps / one_percent_low_fps / p95_ms / p99_ms` 数值合理
  （与游戏体感一致，无 NaN）；
- 采集停止后无残留 ETW 会话（工具只停自己创建的唯一会话）。

**失败处理**：ETW 仍 Access Denied → 记录错误原文，该项标记 blocked，
顺带检查"以管理员身份运行"是否真正生效（`whoami /groups | findstr S-1-16-12288`）。

## 2. V1 — 性能对照实测（Windows 默认 vs phelper）

**现实修订**：本机自 2026-08-25 起无 OGH 前端（无 Appx 包，已核查），
"OGH 顺序对照"按实际可执行形态执行：**基线 = Windows 默认（phelper 不
接管）**，对照 = phelper 各 profile。验收记录必须如实写"OGH 不可用，以
默认状态为对照基线"。

**前置**：V5 通过；固定游戏场景（同一存档/路线/画质，预热完成后再起表）。

**操作**（每轮之间正常退出并确认风扇回固件自动）：

```powershell
# 轮次 0 —— 基线：不启动 phelper（或 --read-only 预览），游戏内 V5 采集 ≥3 次
.\target\release\phelper-desktop.exe --read-only
# 轮次 1-2 —— gaming / cpu-max 各一轮（同场景同时长）：
#   桌面"配置档"页应用 profile → 验证页采集（标签带 profile 名）
# 轮次 3 —— balanced（出厂参考值一键回原厂）确认无回归
```

每轮同时记录：CPU package power / GPU power / 温度 / 风扇 RPM
（验证页 provider 快照或另开 `telemetry --duration <采集秒数>` 对齐时间窗）。

**通过标准**：
- ≥3 组独立报告（基线 + gaming + cpu-max），不挑最好一次；
- 每组含：平均 FPS、1% low、p95/p99、功耗、温度、风扇、节流原因；
- 结论可以是"差异在噪声内"——如实记录数值本身就是验收。

**证据**：`measurements\` 各轮 CSV/JSON + 对照表格写进验收记录。

## 3. V2 — 睡眠/唤醒生命周期

**前置**：管理员会话；`control status` 起点干净。

**操作**（每轮）：

```powershell
# a) 接管一组状态（择一）：
.\target\release\phelper-cli.exe control profile apply gaming --hold 600
#   ——保持该 CLI 进程存活（hold 中），或用桌面实例接管后最小化
# b) 睡眠（管理员窗口仍可发命令；Modern Standby 机型即"睡眠"菜单语义）：
rundll32.exe powrprof.dll,SetSuspendState 0,1,0
# c) 唤醒后立刻在新窗口核对：
.\target\release\phelper-cli.exe control status
type $env:LOCALAPPDATA\phelper\state\control-journal.recovery.json   # 期望无未完成义务
```

**检查点**（唤醒后 status 输出）：
- PPM 全旋钮 VERIFIED 且与睡眠前一致（EPP/EPP1/频率/boost AC+DC）；
- thermal/fan 为 TrustedWrite 且值未漂移（若心跳窗口被睡眠打断，journal
  应有恢复/重断言痕迹——观察而非判错，如实记录）；
- 无 `recovery.json` 残留、无 watchdog 触发（除非温度真实越限）。

**轮次建议**：① profile 接管 + 睡眠；② 手动风扇 + 睡眠（唤醒后 0x2D 回读
应落在目标 ±1000 RPM 内或已按固件自动恢复）；③ 曲线模式 + 睡眠。

**通过标准**：3 轮全部满足检查点；任何恢复失败走 `control restore` 并如实记录。

## 4. V3 — AC/DC 全流程

**前置**：管理员会话；`automation.toml` 配好 AC/Battery profile 与
`battery_efficiency = true`（桌面"自动切换"页配置即写盘）。

**操作**（需要物理拔插适配器，每变化后等稳定 ≥10 s）：

```powershell
# 自动规则切换：
.\target\release\phelper-cli.exe control status   # AC → 应为 ac_profile
# ↓ 拔掉适配器
.\target\release\phelper-cli.exe control status   # → battery_profile 生效；
                                                 #   battery_efficiency 接管 eligible 进程
# 手动覆盖让位：拔电状态下手动应用另一 profile →
#   automation 快照应显示 paused_by_manual（手动优先）
# ↓ 插回适配器
.\target\release\phelper-cli.exe control status   # → 自动恢复或按规则重评估
```

**检查点**：
- 每次切换 journal 有对应 origin（user/automation/shutdown）记录；
- `paused_by_manual` 语义正确：手动接管后自动规则不再覆盖，直到自动侧
  重新接管或用户释放；
- battery_efficiency 的进程接管/释放通过 `os auto status` 的
  managed_processes 数字变化可见；
- 全程 `recovery.json` 无残留。

**通过标准**：拔/插各 ≥2 次全绿；journal 证据完整。

## 5. V6 — BatteryEfficiency 功耗 A/B

**背景**：代码闭环已存在，但"是否真的省电"从未在目标机上证明
（automatic-scheduling-architecture §20）。**结论允许是"收益不显著"**。

**前置**：电池 ≥80% 起点；固定亮度/音量/网络/后台；同一 workload
（建议：`phelper-cli telemetry` 挂着 + 固定一段可重复负载，如同一视频
播放或 `cpu-load --threads N` 基准）；Windows 电源方案不变。

**三组对照**（每组 ≥30 min，电池区间尽量相同）：

```powershell
# 组 1 —— Windows 默认：automation enabled=false（或 Off），记录放电斜率
# 组 2 —— BatteryEfficiency：
.\target\release\phelper-cli.exe os auto battery --hold 0    # Ctrl+C 结束
# 组 3 —— 硬 Affinity 实验对照（仅作参照，风险已知）：
.\target\release\phelper-cli.exe os apply --pid <测试进程> --affinity-group 0 --affinity-mask <E核mask> --hold 0
```

每组采集：`telemetry --duration 1800 --metrics pkg_power,gpu.power,fan,left_rpm`
落盘（`> probe-out\v6-group-N.txt 2>&1`），并每 5 min 记一次
`battery_percent`（脚本化：`Get-CimInstance Win32_Battery` 轮询）。

**通过标准**（§20 的诚实口径）：
- 三组的**任务完成时间**也要记录——E 核拉长执行时间时，瞬时瓦数下降
  不等于总能耗下降；
- 报告给出放电功率对比 + 结论（显著 / 不显著 / 需更严格条件）；
- 结论为"不显著" → Phase E（硬件 profile 联动）按 plan §5 停止推进。

## 6. V4 — MUX 双向重启验证（桌面解禁的唯一门槛）

**前置**：`--features experimental-mux` 的 CLI；当前 MUX = Hybrid（正常出厂态）。

**操作**（完整一个方向）：

```powershell
.\target\release\phelper-cli.exe control status          # 记录 current: Hybrid
.\target\release\phelper-cli.exe control mux discrete
# 检查待重启记录已落盘（status 的 mux lifecycle 行 + mux.json）：
type $env:LOCALAPPDATA\phelper\state\control-journal.mux.json
# ↓ 操作者手动重启机器（本工具不自动重启）
# 重启后（管理员会话）：
.\target\release\phelper-cli.exe control status          # current: Discrete？
#   通过 → status 应显示该方向已核验；随后反向重复：
.\target\release\phelper-cli.exe control mux hybrid
#   ↓ 重启 → status 核对 Hybrid + 双向记录完整
```

**纪律**（mux.json 生命周期已实现）：
- **重启前读到目标不算成功**——固件返回的是"请求受理"，不是"已切换"；
- 重启后必须由 status 核验，核验通过才标记该方向 verified；
- BIOS 变化使既有记录失效，需重新验证；
- 没有自动强制回滚、"已验证"标记绕过开关——全手动。

**通过标准**：两个方向各一次"写 → 重启 → status 核验"全绿，mux.json 双向
记录完整 → 满足 plan §6 的桌面解禁三条件（代码门已就绪，仅差本验证）。

## 7. V7 — 软件风扇曲线实机 soak

**背景**：曲线已是内置档语义（M7），但"长时高负载 + 睡眠 + 强杀"的 soak
仍是进入更多默认场景前的验收项（architecture §41.4）。

**操作**（三段）：

```powershell
# 段 1 —— 长高负载（≥45 min）：应用含曲线的 profile（gaming/silent），
#         叠加编译/cpu-load/游戏负载；每 5 min 记录一次：
.\target\release\phelper-cli.exe control status   # 曲线目标 vs 0x2D 回读偏差
# 段 2 —— 睡眠唤醒（复用 V2 曲线轮）
# 段 3 —— HIL 资产重放（M2 遗留脚本，可重跑）：
.\docs\hil8-fan-hold.ps1        # 125 s hold 撑过 clawback 窗口
.\docs\hil910-clawback.ps1      # taskkill /F → 固件 ~120 s 自动收回
.\docs\hil13-hysteresis.ps1     # ≥90 °C 强制满速 / ≤85 °C 释放
.\docs\hil14-watchdog-gate.ps1  # 传感器冻结看门狗 fail-closed
```

**检查点**：曲线目标与回读持续一致（±1000 RPM 容差）；迟滞触发/释放
journal 证据完整；强杀后风扇回到固件自动（idle 0 RPM 为正常态）。

**通过标准**：三段全绿后，曲线语义可从"用户显式选择"升级进更多默认
场景（是否写进更多内置档属后续决策，本 soak 只解锁可能性）。

## 9. V9 — 资源占用 fresh soak

**背景**：CLAUDE.md 明确 v0.2 的 2.7% CPU / 183 MB 数字对当前 7 页面 shell
**过时**，需 release 构建重测（debug 数字无意义）。

**操作**（release 桌面，管理员启动）：

```powershell
# 正确的 CPU 测量法（CLAUDE.md 教训：必须从 $p.CPU 差值算，绝不能读瞬时值）：
$p = Get-Process phelper-desktop; $c0 = $p.CPU; $t0 = Get-Date
Start-Sleep -Seconds 480                      # Dashboard 驻留 8 min
$p.Refresh(); $cpuPct = ($p.CPU - $c0) / ((Get-Date) - $t0).TotalSeconds * 100 / $env:NUMBER_OF_PROCESSORS
"Dashboard 8min: {cpuPct:N2}%  RAM {workingset/1MB:N0} MB"
# 变体：各页面切换浏览 2 min/页（Performance/Validation/Automation/Hardware/
#       Profiles/Settings），每页结束记录一次；再回 Dashboard 4 min 看趋势
```

**通过标准**：Dashboard ≤5% CPU 目标带（v0.2 为 2.7%，新 shell 页面更多，
如实记录实测）；RAM 8 min 内无 >10 MB 的持续爬升（v0.1 曾 +19 MB/8 min，
v0.2 已大幅收敛）；关闭→优雅退出全程 ≤40 s（有 stage-timing 日志自证）。

**失败处理**：超过目标带 → 记录数值与页面分布，W-B 追加一轮渲染层优化
（不阻塞 V1–V8 的验收）。

## 10. agent 协助模式（可选）

所有 CLI 侧步骤可以在本仓库会话中由 agent 代跑：UAC 提权 + 输出重定向
（`Start-Process -Verb RunAs` + `cd /d` 绝对路径，教训已踩过）。分工：

| agent 可代跑 | 必须用户动手 |
|---|---|
| probe / control status / telemetry / profile apply / journal 与报告收集 / 分析 | **UAC 确认、游戏场景操作、拔插适配器、睡眠与唤醒、重启 ×2（V4）、taskkill**（涉及强杀进程的按项目纪律由用户执行） |

每完成一项，验收记录按 §0 总则追加进 [`ogh-milestones.md`]。
